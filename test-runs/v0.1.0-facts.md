## #66 feat: report what a run does and what it costs

Makes the tool measurable, so the defaults can be decided by data instead of guesswork.

Every `preview` and `generate` run now ends with:

```text
Run metrics
  Rule-based check: 3 runs, 1 with findings, 1 claim, no tokens
  Thorough check:   3 runs, 2 with findings, 2 claims, 6,230 in / 130 out
    caught 1 claim the rule-based check missed, for 6,360 tokens in 3 calls
  Rephrasing:       3 calls, 5,437 in / 859 out
  Total:            12,656 tokens
```

## Does the thorough check earn its cost?

The indented line is the point of the whole summary. It pairs the claims **only** the thorough check caught with the tokens it spent catching them. Claims both checks find are excluded, because on those the thorough check adds nothing over the free one. Read across a few real releases, that line answers the question directly: consistently zero claims caught means the tokens buy nothing.

## What changed

- `Chartula.Core/Observability/`: `IRunMetrics` with the `RunMetrics` sink, `NullRunMetrics`, `RunReport` and `RunReportFormatter`.
- `ChatModel` reports token usage, because it is the only place that sees it. Usage is attributed per `LlmOperation`, so the check's cost is readable on its own; a provider that reports no usage still has its call counted.
- `ReleasePipeline` records both checks' findings in one call, because it is the only place that can compare them, and returns the report on `ReleaseOutcome`.
- Measurement is a side channel: the sink is optional everywhere, and a run without one produces byte-identical output.
- `docs/run-metrics.md` explains how to read the summary and make the keep-or-drop call.

## #67 chore: replay stored fact bases so the pipeline is tested for free

Stored fact bases the pipeline can be replayed against, so the suite runs as often as wanted at zero token cost.

## Fixtures are ordinary `changelog.json` files

No second format: a fixture is exactly what a run writes. A real release can be frozen into one by copying the `changelog.json` a run produced. `DeserializeFactBase` is the inverse of `Serialize` and now exists for it, refusing unknown schema versions and categories with a clear message.

A test re-serializes every fixture and compares it to the file on disk, because a fixture that has drifted from what a run writes has stopped representing one. That test earned its keep immediately: it caught that the hand-written fixtures were not what the writer produces.

`Chartula.Core` depends on `Microsoft.Extensions.AI` alone - no provider package - and the fixture tests live in `Chartula.Core.Tests`. Reaching a real model from there is not something the tests avoid by discipline; it is not possible.

Everything downstream of the facts is the production type: generator, renderer, formatter, both checks, review, writers. Only the model is a stand-in: `EchoingChangelogModel` invents nothing (so any flag is the checker's doing), `InventingChangelogModel` invents a fact (so the checks are proven to still bite, not just to leave clean input alone), and `UnreachableChangelogModel` throws if reached, which turns "this path costs no tokens" into something the suite enforces.

## #70 fix: two release blockers found by dogfooding v0.1.0

Found by running `chartula preview --tag v0.1.0` against this repository. Neither bug is reachable from the existing tests: the first needs a live API call, the second needs real pull request bodies.

## Truncation (`ChatModel`)

Calls went out without `ChatOptions`, so `MaxOutputTokens` was never set. The provider requires `max_tokens` and substitutes its own default of 1024 when absent. All three audience texts were cut off mid-word — the run metrics showed `3 calls, 3,072 out`, exactly 3 × 1024.

It failed silently. The run reported success, and the thorough check spent 56,712 tokens flagging the severed sentence as an unsupported claim — a real bug symptom read as a hallucination.

The ceiling is now always sent, configurable via `llm.maxOutputTokens`, defaulting to 16000.

## False breaking changes (`ConventionalCommitCategorizer`)

`MentionsBreakingChange` searched the whole body for `BREAKING CHANGE` as a case-insensitive substring, so prose *discussing* breaking changes *declared* one. Six of the thirty-three changes in v0.1.0 were mislabelled; none were breaking. #65 described a setting called breaking-change prominence and was marked breaking for saying so — the feature that renders breaking changes prominently became one.

Now matches the Conventional Commits footer: uppercase, start of line, colon-terminated.

## Verification

Both fixes confirmed against a real run, not just tests:

| | Before | After |
| --- | --- | --- |
| Rephrasing output | 3,072 tokens (3 × 1024) | 11,271 tokens |
| Text endings | mid-word | complete sentences |
| Breaking changes reported | 6 | 0 |
| Thorough check claims | 1 (the truncation artifact) | 0 |

265 tests pass, 9 new. The categorizer regression test uses the sentence from #65 verbatim as a fixture.

## Known, not fixed here

`RuleBasedFaithfulnessChecker` matches `\bbreaking\b` across the whole output and flags a breaking-change claim whenever the word appears — the same phrase-versus-assertion mistake, now visible because no fact is breaking anymore. The flags are advisory and do not fail a run, and separating a claim from prose that uses the word needs more than a regex. Filed separately rather than rushed in.
