### What's New

- **Configuration file**: Chartula can now be configured with a `chartula.yaml` (or `.yml`) file covering every option the tool exposes, instead of only environment variables. The tool still runs with sensible defaults when no file is present, and an invalid value in it now stops the run with a plain "Configuration error" message instead of a crash.
- **`preview` and `generate` commands**: `chartula preview` and `chartula generate` are now available, each taking a `--tag` and `--repo` option to target a release. `preview` shows the full result without writing or publishing anything, so you can check a changelog before it goes anywhere, while `generate` writes and publishes it.
- **`--no-publish` flag**: `chartula generate --no-publish` writes the local output files without publishing release notes, and the run lists what it wrote alongside what it skipped. You can reproduce a release's output repeatedly without republishing it each time.
- **Machine-readable record**: Every run now writes a `changelog.json` file recording the full input facts and the generated text for all three audiences, giving you a record of exactly what produced a release's changelog.
- **`CHANGELOG.md`**: Each release now adds a new section to the top of `CHANGELOG.md`, keeping every earlier section intact. Running the same release again replaces its own section in place instead of duplicating it, so re-running `generate` won't corrupt your history.
- **GitHub release notes**: `chartula generate` now writes the generated text to the release's notes on GitHub, creating the release first if it doesn't exist. Running it again for the same tag updates that release instead of creating a duplicate.
- **Customer release page**: Each run also writes a `release-<tag>.md` file - a publishable page for the customer changelog with a title, short description and publication date at the top. No page is written when a release has nothing to say to that audience, and the file is written even under `--no-publish`, since producing it doesn't publish anything on its own.
- **Change discovery with fallback**: For each release, Chartula reads the commits since the previous tag (or the whole history for a first release) and turns every merged pull request into a changelog entry with its title, description, labels and link. Where a commit has no matching pull request, or a pull request's title is blank or uninformative, the entry falls back to the commit message or the pull request's body instead of being skipped.
- **Automatic categorization**: Each change is placed into a category based on its Conventional Commit prefix, such as `feat` or `fix`. Anything that doesn't match a recognized prefix falls under a general "Other" category rather than being mis-classified.
- **Fact depth setting**: A `factBase.depth` setting, set in `chartula.yaml`, controls how much of each pull request feeds the changelog - title only, title and description (the default), or title, description and linked issues.
- **Label rules**: Labels on a pull request can now steer curation, set in `chartula.yaml` - a label can exclude a pull request, force it into a chosen category, or you can require every included change to carry a label. None of this is required; the tool works the same with no labels in use.
- **Default filtering**: Internal and chore-type changes are left out of the changelog by default, and which categories are excluded can be changed in `chartula.yaml`. A genuine breaking change is never left out, even if its category would otherwise be excluded.
- **Category display settings**: A `categories` section in `chartula.yaml` lets you set the order categories appear in, rename their display names, and control whether breaking changes stand out prominently, which is on by default.
- **Facts-only rephrasing**: Generated text only rephrases the facts collected for a release - it never invents a fact, number or name that isn't in that list, and when the facts are thin, the text stays short instead of being padded out.
- **Three audience versions**: Every release now produces three separate texts from the same facts - technical, with full detail and links; customer-facing, in plain language and omitting internal-only changes; and product, grouped by theme - so the three can't contradict each other.
- **Free accuracy check**: A fast check that costs no tokens now flags a number or a quoted name in the generated text that isn't backed by the underlying facts. It always runs.
- **Thorough accuracy check**: A second, LLM-based check now reviews each generated text against its facts, catching meaning-level errors a simple comparison would miss. It runs by default and can be turned off in `chartula.yaml` if you don't want it.
- **Review mode**: An optional review mode can be turned on in `chartula.yaml` to show you each generated text with any flagged passages before it's written, so you can approve it as-is or edit it. It stays off unless you enable it.
- **Run metrics summary**: Every `preview` and `generate` run now ends with a summary showing how many calls each check made, how many claims it found, and how many tokens and how much cost each check and the rephrasing step used. This lets you see whether the thorough check is finding anything the free check doesn't.
- **GitHub token warning**: Starting a run without a `GITHUB_TOKEN` set now prints a warning explaining that GitHub allows only 60 requests an hour without one, that a release can use up that budget partway through, and how to set one. The run isn't blocked - a token stays optional for a small release - and the warning goes to standard error, so redirecting the changelog output to a file still leaves it visible.
- **OpenAI-compatible provider**: `llm.provider` now accepts `openai-compatible`, letting a release be generated through any endpoint speaking that dialect, including a model run on your own machine where release data doesn't leave it. Neither the model nor the `llm.baseUrl` endpoint has a default for this provider, so both need to be set explicitly in `chartula.yaml`, and a clear error names whichever one is missing.
- **Thinking setting**: An `llm.thinking` setting, set in `chartula.yaml`, lets you choose `provider-default` (today's behavior), `disabled`, or `adaptive`. Choosing a value your model doesn't support fails the run outright rather than silently falling back.

### What's Changed

- **Customer changelog ordering**: Entries in a generated customer changelog that ask you to do something now appear before ones that don't, a breaking change always leads, and unrelated minor changes are gathered under a single note instead of each getting its own line.
- **Slow-model timeout**: A call to a slow-responding model no longer fails after 100 seconds; Chartula now waits up to 10 minutes for a response before giving up.
- Also: a configured base URL missing its `http://` or `https://` scheme is now rejected immediately, instead of failing later in a way that pointed away from the setting that caused it.

### Bug Fixes

- **Truncated generated text**: Generated text could be cut off mid-word because no output limit was sent with a request, so the provider silently applied its own low default. Every request now sends an explicit ceiling, defaulting to 16,000 tokens and adjustable via `llm.maxOutputTokens` in `chartula.yaml`, so text is no longer cut short.
- **False breaking-change labels**: A pull request that merely discussed breaking changes in its description could be labeled as a breaking change itself. Only a proper Conventional Commits breaking marker - a `!`, a `breaking` type, or a `BREAKING CHANGE` footer - now counts, so a change is flagged breaking only when it actually declares one.
- **False breaking-change flags in generated text**: The free check used to flag any generated text that merely mentioned the word "breaking," even when it was describing a feature or setting by that name. That flag has been removed; breaking-change claims are now judged only by the thorough check, which can tell a mention apart from an actual claim.
- **Unreadable thorough check looked clean**: When the thorough check's response couldn't be understood, a run used to report it as clean with nothing found, indistinguishable from a check that genuinely found nothing. The run summary and review flags now say when a check came back unreadable, so you can tell the two apart.
- **Missing customer page**: A run could produce an empty customer changelog, and no page for it, when the model's whole answer read as a description with nothing left underneath. That text is now kept as the body instead, so a real customer rendering is no longer discarded.
- **Miscounted LLM calls**: An LLM call that went unreported in the run summary could look identical to one that made no call at all. The two are now told apart, so a run's totals stay accurate.
- **Inconsistent customer entries**: Customer changelog entries could come out with no fixed shape between runs, sometimes leaving out the sentence stating what you could now rely on. Entries now follow a fixed structure with that sentence required, so every entry states what changed and what you can count on because of it.
