Preview changelog for v0.1.0

--- Technical ---
## Features

- **Run metrics for every `preview` and `generate` run** — Each run now ends with a `Run metrics` summary covering rule-based check runs/findings/claims, thorough check runs/findings/claims and token usage, rephrasing calls, and a token total. The indented line pairs the claims **only** the thorough check caught with the tokens spent catching them; claims found by both checks are excluded, since the thorough check adds nothing there. Adds `Chartula.Core/Observability/` with `IRunMetrics`, the `RunMetrics` sink, `NullRunMetrics`, `RunReport` and `RunReportFormatter`. `ChatModel` reports token usage, attributed per `LlmOperation` so each check's cost is readable on its own; a provider that reports no usage still has its call counted. `ReleasePipeline` records both checks' findings in a single call and returns the report on `ReleaseOutcome`. Measurement is a side channel: the sink is optional everywhere and a run without one produces byte-identical output. Documented in `docs/run-metrics.md`. Closes #26 ([#66](https://github.com/goldbarth/chartula/pull/66))

- **`categories` configuration section** — Category presentation is now configurable alongside the existing `labels`, `factBase` and `faithfulness` sections. `CategorySettings` in the domain holds category order, display names and breaking-change prominence, with `From(...)` parsing raw configuration values and rejecting unknown category names with a clear message. The `categories` section in `chartula.yaml` supports `order`, `names` and `breakingProminent` (default `true`); every section remains independently editable and untouched sections keep their defaults. `GroundedFactsFactory` is extracted out of `ReleaseChangelogGenerator` so audience filtering, category ordering and display naming have a single home. Documented in `docs/configuration.md`. Closes #25 ([#65](https://github.com/goldbarth/chartula/pull/65))

- **`chartula.yaml` configuration file support** — `AddChartulaYaml` in `Chartula.Cli` loads `chartula.yaml` (or `.yml`) via YamlDotNet and flattens it into `Chartula:*` configuration keys, layered *before* environment variables so env overrides YAML. The existing section options (`llm`, `github`, `labels`, `filter`, `factBase`, `faithfulness`, `review`) are unchanged — this adds the file as a source. With neither a file nor env vars, every option binds to its default. Ships `chartula.example.yaml` at the repo root (minimal, everything commented out) rather than a live `chartula.yaml`, so it is not picked up when running Chartula in its own repository; full options live in `docs/configuration.md`. Configuration errors such as an invalid value in `chartula.yaml` are now reported as a clear `Configuration error: ...` message instead of an unhandled exception. Adds the `Chartula.Cli.Tests` project (`InternalsVisibleTo` from the CLI) as the home for CLI-level tests. Closes #24 ([#64](https://github.com/goldbarth/chartula/pull/64))

- **`generate` and `preview` commands wired to the pipeline** — `ReleasePipeline` in `Chartula.Core` orchestrates the flow over ports only: read commit range and PRs, build the fact base, render all audiences, run the rule-based and thorough faithfulness checks plus review, then write outputs. The only difference between the two modes is the final write step: `generate` writes `changelog.json` (all audience texts), `CHANGELOG.md` and the GitHub release notes from the technical rendering, while `preview` runs the identical flow — including generation, so the real result is visible — and writes or publishes nothing. `Chartula.Cli` exposes `chartula preview` / `chartula generate`, each taking `--tag` and `--repo <owner/name>`, with a usage screen, clear errors for unknown commands and missing options, and a per-audience summary. Pipeline errors are caught and reported rather than crashing. `--repo` is explicit for now; auto-detecting it from the git remote is future work. The interactive console reviewer is not wired here — review mode still uses the auto-approve reviewer until interactive stdin review is built. Closes #23 ([#63](https://github.com/goldbarth/chartula/pull/63))

- **All audience texts stored in `changelog.json`** — `ChangelogDocument` gains a `renderings` object keyed by audience (`technical` / `customer` / `product`), written in a fixed order, keeping the customer and product-manager texts inside the one file instead of as separate marketing files in the repo. `ChangelogJsonSerializer.Serialize` and the `IChangelogJsonWriter` port take an optional renderings map; when none are provided the object is present but empty. Change entries remain deterministic facts — only `renderings` is LLM-produced text. `schemaVersion` stays **1**: per the documented stability contract, adding an optional field is non-breaking and old consumers ignore `renderings`. Documented in `docs/changelog-json.md`. Closes #22 ([#62](https://github.com/goldbarth/chartula/pull/62))

- **Generated text written back to GitHub release notes** — Adds the `IReleaseNotesWriter` port in `Chartula.Core` (reusing `RepositoryCoordinates`) and `GitHubReleaseNotesWriter` in `Chartula.Infrastructure`, built on the GitHub REST API with plain `HttpClient` and source-generated JSON (AOT-friendly). It calls `GET /releases/tags/{tag}`, then either `PATCH /releases/{id}` to update in place or, on 404, `POST /releases` to create with `tag_name` + `body`, returning the release's `html_url`; API and network failures become clear `InvalidOperationException`s. Because GitHub keys a release by its tag, re-running for the same tag takes the found path and updates that one release's notes rather than creating a second release. The GitHub `HttpClient` setup is extracted into a shared `GitHubHttpClientFactory` used by both the PR reader and the release-notes writer. Closes #21 ([#61](https://github.com/goldbarth/chartula/pull/61))

- **`CHANGELOG.md` written with history prepended and preserved** — `ChangelogMarkdownComposer` (pure logic in Core) composes new file content from the existing file and a release: the new section is prepended at the top, existing sections are kept verbatim, and re-running the same tag replaces that section in place rather than duplicating it — idempotent, never reordering history, so re-running an older release after a newer one does not move it above the newer one and running the same release twice yields a byte-identical file. A brand-new file gets a `# Changelog` title. Adds the `IChangelogMarkdownWriter` port in Core and `FileChangelogMarkdownWriter` in `Chartula.Infrastructure`, which reads the existing file and writes the composed result — the same split as `changelog.json`: format logic in Core, file I/O in Infrastructure. Closes #20 ([#60](https://github.com/goldbarth/chartula/pull/60))

- **Opt-in review mode for human sign-off of flagged passages** — `IReviewCoordinator`/`ReviewCoordinator` gate each rendering on an opt-in toggle. With review off (the default) the text passes straight through, approved as-is, and the reviewer is never consulted; with review on the item goes to an `IReviewer` that either approves it as-is or returns an edited version, and the coordinator returns that `ReviewDecision` whose `Text` is what gets written. `ReviewPresentation` formats an item for a maintainer as the generated text followed by the highlighted flagged passages from the rule-based and thorough checks. `AutoApproveReviewer` is the non-interactive default; the interactive console reviewer ships with the CLI command surface. `Chartula.Cli` binds the `Chartula:Review` toggle and registers the coordinator. Closes #19 ([#59](https://github.com/goldbarth/chartula/pull/59))

- **Thorough second-pass LLM faithfulness check with a toggle** — `IThoroughFaithfulnessChecker`/`ThoroughFaithfulnessChecker` run a second LLM pass via `CheckFaithfulnessAsync`, turning the fact base into grounded facts and flagging unsupported claims — catching meaning-level distortions the rule-based check cannot see, such as "bug fixed" rendered as "security hole closed". When the toggle is off, or there is nothing to check, it returns a faithful report with no LLM call. `ThoroughFaithfulnessOptions(Enabled = true)` is on by default and can be disabled via the `Chartula:Faithfulness:Thorough` config key. The faithfulness prompt moves from an inline placeholder in `ChatModel` into `IChangelogPromptBuilder.BuildFaithfulnessPrompt`, with its text in the Prompts partial and an explicit meaning-level-distortion instruction. Removing the toggle or adding more granular check settings is deferred until observability data exists. Closes #18 ([#58](https://github.com/goldbarth/chartula/pull/58))

- **Rule-based faithfulness check for obvious hallucinations** — `IRuleBasedFaithfulnessChecker`/`RuleBasedFaithfulnessChecker` check generated output against the fact base and return a `FaithfulnessReport`, flagging: a number in the output not present in the facts (allowed numbers include PR numbers, linked issues, and any number in titles, descriptions or the tag); a quoted or backticked name absent from the facts (the usual shape of an invented API, feature or option name); and a breaking-change claim when no fact is marked breaking. Flags are advisory — they surface passages for review rather than hard-failing. The checker has no `IChangelogModel` dependency and is constructed with no arguments, so there is structurally nothing to call: it costs zero tokens and always runs, with no toggle. Uses source-generated regexes (AOT-friendly). Closes #17 ([#57](https://github.com/goldbarth/chartula/pull/57))

- **Consistent formatting and tone per audience** — `IChangelogFormatter`/`ChangelogFormatter` in `Chartula.Core` normalize model output with conservative, structure-preserving rules — normalized line endings, a single `- ` bullet marker, trimmed trailing whitespace, collapsed blank-line runs — while leaving non-bullet lines such as headings and prose intact. The generator applies the formatter to every rendering, so formatting is consistent regardless of what the model returns. Tone normalization comes from a new prompt rule instructing the model to write in one consistent voice and format and not to carry over an individual author's tone or phrasing. Splitting it this way makes formatting consistency deterministic and testable with a stubbed model. Closes #16 ([#56](https://github.com/goldbarth/chartula/pull/56))

- **Technical, customer and PM renderings from one fact base** — `IReleaseRenderer`/`ReleaseRenderer` render all three audiences from the same `FactBase`, delegating to the generator with one call per audience and returning a result per `Audience`; a failure in one audience does not fail the others. Audience selection is deterministic in code rather than left to the LLM: customer omits non-user-visible changes and their links, technical keeps the pull request link and the full change set, and product sees the full set. Technical prompt guidance now also asks to keep links, customer is benefit-focused and PM groups by theme. Because every audience is derived from the same established, deterministic facts, two renderings cannot disagree on what changed. Closes #15 ([#55](https://github.com/goldbarth/chartula/pull/55))

- **Prompt architecture that rephrases facts and never invents** — `IChangelogPromptBuilder`/`ChangelogPromptBuilder` produce a `ChangelogPrompt` (system + user). The system prompt pins the model to rephrasing: never introduce a fact, number or name not in the list; treat each fact's category and `(breaking)` marker as established, using them as given without changing or inferring them; on thin facts stay brief without padding, speculating or inventing; no preamble or conclusion — plus per-audience guidance. The user prompt carries only the facts, with nothing added by our code to pad them. `ChatModel` now delegates to the builder and simply wires the prompt into the `IChatClient`. Categories and flags reach the model as text embedded by the generator; the prompt presents them verbatim and instructs the model not to decide them. Closes #14 ([#53](https://github.com/goldbarth/chartula/pull/53))

- **Changelog generation through the provider interface** — `IReleaseChangelogGenerator`/`ReleaseChangelogGenerator` and `ChangelogGenerationResult` turn the fact base into grounded fact statements and make exactly one `IChangelogModel.RephraseAsync` call per release; an empty fact base makes no call at all. Provider failures are caught and returned as a failed result carrying the release tag and the provider message, while cancellation propagates rather than being swallowed. The generator depends only on `IChangelogModel` and references no provider type; the fact-to-statement mapping is a plain fact carrier, with prompt design and audience-specific rendering out of scope here. Closes #13 ([#52](https://github.com/goldbarth/chartula/pull/52))

- **Fact base serialized to `changelog.json`** — Writes the release fact base as a durable, machine-readable record and a source for later outputs. `ChangelogDocument` in Core defines the stable on-disk shape (`schemaVersion` + `tag` + `changes`), kept separate from the domain `FactBase` so the domain can evolve without breaking the file format. `ChangelogJsonSerializer` converts `FactBase` to JSON and back — pure, deterministic and source-generated (AOT/trim-safe), writing the category as its name for a stable, readable record. Adds the `IChangelogJsonWriter` port in Core and `FileChangelogJsonWriter` in `Chartula.Infrastructure` for file I/O only. `schemaVersion` (currently `1`) is the contract: consumers read it and reject versions they do not understand; fields are always present including `null` values, adding optional fields is non-breaking, and removing, renaming or re-meaning a field bumps the version. Every field is a deterministic fact — nothing in the file is LLM-generated. Documented in `docs/changelog-json.md`. Closes #12 ([#51](https://github.com/goldbarth/chartula/pull/51))

- **Configurable fact-base depth** — `FactBaseDepth` offers three modes plus a `FactBaseDepthParser`: `TitleOnly` (title only), `TitleAndDescription` (the default — title and description, no issues) and `TitleDescriptionAndIssues` (title, description and linked issues). `FactBaseBuilder` honours the depth, taking the description from the middle mode up and linked issues only in the deepest mode. `Chartula.Cli` reads `Chartula:FactBase:Depth` and passes the parsed value into the builder; the parser accepts the canonical names plus the aliases `title`, `description` and `full`, and raises a clear error on an unknown value. Because a depth is a config value (an enum), it is passed into the builder via a factory rather than registered as its own DI service. Whether all three modes survive long-term is revisited with real data; the option set is not expanded here. Closes #11 ([#50](https://github.com/goldbarth/chartula/pull/50))

- **Curated changes transformed into the release fact base** — `IFactBaseBuilder`/`FactBaseBuilder` and the `FactBase` container (tag plus one `ChangeFact` per included change) assemble the grounded fact base for a release. The builder resolves changes with the missing-PR fallback, drops filtered-out changes and maps each survivor to a `ChangeFact`. Category and breaking flag come from deterministic categorization, and a label can force the category. `IsUserVisible` is derived from the category — outward-facing categories, plus every breaking change. `LinkedIssues` are parsed from GitHub closing keywords (`closes`/`fixes`/`resolves #n`) in the title and body. Category and flags come from the deterministic curation steps, never from an LLM: the builder has no LLM dependency. Closes #10 ([#49](https://github.com/goldbarth/chartula/pull/49))

- **Fact-base data model (an index card per change)** — `ChangeFact` in `Chartula.Core` is one structured object per change and the single source of truth the LLM may only rephrase from, capturing title, PR number, link, category (from deterministic categorization), user-visible flag, breaking flag, linked issues, and an optional description populated per the fact-base depth. Every field is derived deterministically and nothing in the model is LLM-generated; PR-only fields (number, link) are nullable so commit-based changes fit the same shape. The model is serializable. The release-level container is assembled when curated PRs are transformed into facts, and the whole base is serialized to `changelog.json` separately. Closes #9 ([#48](https://github.com/goldbarth/chartula/pull/48))

- **Internal and chore changes dropped by default** — `IChangeFilter`/`ChangeFilter` and `ChangeFilterRules` combine deterministic categorization with label rules. Decision order: a label that excludes the change wins outright; a breaking change is never dropped; otherwise the change is dropped when its effective category — a label-forced one, else the deterministic one — is in the excluded set. The default excluded set is `Internal`, overridable via `Chartula:Filter:ExcludeCategories`, where an explicit (possibly empty) list replaces the default. Never dropping a breaking change is a deterministic safeguard driven by the breaking flag rather than guesswork, matching the intent to show breaking changes prominently; an explicit label exclusion still wins over it. `Chartula.Cli` binds the `Chartula:Filter` section and registers the filter. Closes #8 ([#47](https://github.com/goldbarth/chartula/pull/47))

- **Curation steered by label rules from config** — `LabelRules` (excluded labels, label-to-category overrides, only-include-labeled mode) plus `ILabelRulePolicy`/`LabelRulePolicy` produce a `LabelDecision` carrying an include flag and an optional forced category. Precedence: exclusion wins, then only-labeled drops unlabeled changes, otherwise the change is included with the first matching label deciding a forced category. Everything is optional — `LabelRules.None` ignores labels entirely so the tool works with no labels at all — and matching is case-insensitive. `Chartula.Cli` binds the `Chartula:Labels` section into `LabelRules` via `LabelRules.From`, which parses category names and reports a clear error on an unknown one, and registers the policy. Closes #7 ([#46](https://github.com/goldbarth/chartula/pull/46))

- **Deterministic categorization ahead of the LLM** — `IChangeCategorizer` and `ConventionalCommitCategorizer` decide the kind of each change in code before any generation, so the model can never invent it. The categorizer reads Conventional Commit conventions from the change title (`type(scope)!: subject`) and assigns a `ChangeCategory`: Feature (`feat`), Fix (`fix`), Performance (`perf`), Documentation (`docs`), Refactor (`refactor`), Internal (`build`/`ci`/`chore`/`test`/`style`/`revert`), with **Other** as the sane default for unrecognized or prefix-less titles. Breaking is tracked separately as `ChangeClassification.IsBreaking` via a `!` marker, a `breaking` type or a `BREAKING CHANGE` body note, so a breaking feature stays a feature while still being flagged. Pure and deterministic with no LLM and no I/O, using a source-generated regex (AOT-friendly). Closes #6 ([#45](https://github.com/goldbarth/chartula/pull/45))

- **Graceful degradation when clean PRs are missing** — `IReleaseChangeResolver` and `ReleaseChangeResolver` turn a `CommitRange` and the merged `PullRequestInfo` list into `ReleaseChange` values (title, description, number, url, labels, `ChangeSource`, commit sha) as pure domain logic with no I/O. With merged PRs present there is one change per PR (`Source = PullRequest`); with no PRs at all, one change per commit using the commit subject (`Source = Commit`). A blank or uninformative PR title (for example `WIP`, `update`, `Merge ...`) falls back to the PR body's first informative line, then to a generic `PR #n`. An empty release yields an empty set rather than an exception. The uninformative-title heuristic is a small starter set that becomes configurable with the config work. Closes #5 ([#44](https://github.com/goldbarth/chartula/pull/44))

- **Merged pull requests for a release fetched from the GitHub API** — Adds the `IReleasePullRequestReader` port in `Chartula.Core` plus `PullRequestInfo` (number, title, description, labels, url) and `RepositoryCoordinates`. `GitHubPullRequestReader` in `Chartula.Infrastructure` queries GitHub's "pull requests associated with a commit" endpoint for the commits in a `CommitRange`, keeps merged PRs only and de-duplicates by number, with DTOs parsed via a source-generated `System.Text.Json` context. The composition root in `Chartula.Cli` configures the `HttpClient` (base URL, GitHub headers, bearer token by env-var name) and registers the reader. Raw `HttpClient` plus `System.Text.Json` source generation was chosen over Octokit as dependency-light and native-AOT friendly, consistent with the git-CLI choice, and a stub `HttpMessageHandler` makes it fully mockable without network. The token is read by env-var name (`GITHUB_TOKEN`) and is optional — public repos work unauthenticated, subject to rate limits. API status, network and malformed-response paths all raise a clear `InvalidOperationException` instead of crashing. Fallback when clean PRs are missing is out of scope. Closes #4 ([#43](https://github.com/goldbarth/chartula/pull/43))

- **Release commit range read from git** — Adds the `IReleaseCommitReader` port in `Chartula.Core` plus `CommitInfo` and `CommitRange` (with `IsFirstRelease`) as pure domain with no I/O, and a new `Chartula.Infrastructure` layer whose `GitCliCommitReader` shells out to `git` for the range since the previous tag (`<prev>..<tag>`), or all history up to the tag when there is no previous tag (first release), with clear errors for unknown and blank tags. The `Chartula.Cli` composition root registers the git reader while the pipeline depends only on the port. The git CLI was chosen over LibGit2Sharp to avoid native dependencies that would fight the planned native-AOT binaries, and `git` is present in any repo Chartula runs on. `Chartula.Infrastructure` is the new home for concrete I/O adapters — keeping `Core` pure domain and `Cli` a thin composition root — and will later host the GitHub API, file writers and webhooks. Closes #3 ([#42](https://github.com/goldbarth/chartula/pull/42))

- **LLM provider abstracted behind `IChangelogModel`** — Adds the new `Chartula.Core` project with the provider-agnostic LLM seam the pipeline builds on: `IChangelogModel` (`RephraseAsync`, `CheckFaithfulnessAsync`) as the interface the pipeline depends on, `ChatModel` as the single implementation backed by a provider-agnostic `Microsoft.Extensions.AI.IChatClient`, and the domain types `Audience`, `GroundedFacts`, `RephraseRequest`, `FaithfulnessRequest` and `FaithfulnessReport`. The `Chartula.Cli` composition root wires Anthropic as the first provider via `AsIChatClient`, with model and provider selectable via config and the API key read by env-var name — the only provider-specific code, so swapping providers is a composition-root change only. Adds the `Chartula.Core.Tests` project, which exercises the seam with a stub `IChatClient` and no live provider call. `GroundedFacts` and the `ChatModel` prompts are intentionally minimal placeholders; the fact base and prompt design are tracked separately. Closes #2 ([#41](https://github.com/goldbarth/chartula/pull/41))

## Fixes

- **Two release blockers found by dogfooding v0.1.0** — Both were found by running `chartula preview --tag v0.1.0` against this repository and neither is reachable from the existing tests: the first needs a live API call, the second real pull request bodies.
- *Truncation in `ChatModel`*: calls went out without `ChatOptions`, so `MaxOutputTokens` was never set. The provider requires `max_tokens` and substitutes its own default of 1024 when absent, cutting all three audience texts off mid-word — the run metrics showed `3 calls, 3,072 out`, exactly 3 × 1024. It failed silently: the run reported success and the thorough check spent 56,712 tokens flagging the severed sentence as an unsupported claim, a real bug symptom read as a hallucination. The ceiling is now always sent, configurable via `llm.maxOutputTokens` and defaulting to 16000.
- *False breaking changes in `ConventionalCommitCategorizer`*: `MentionsBreakingChange` searched the whole body for `BREAKING CHANGE` as a case-insensitive substring, so prose *discussing* breaking changes *declared* one. Six of the thirty-three changes in v0.1.0 were mislabelled and none were breaking; #65, which described a setting called breaking-change prominence, was marked breaking for saying so. Matching now follows the Conventional Commits footer: uppercase, start of line, colon-terminated.

  Confirmed against a real run rather than tests alone: rephrasing output went from 3,072 tokens (3 × 1024) to 11,271, text endings from mid-word to complete sentences, reported breaking changes from 6 to 0, and thorough check claims from 1 (the truncation artifact) to 0. The categorizer regression test uses the sentence from #65 verbatim as a fixture. Known and deliberately not fixed here: `RuleBasedFaithfulnessChecker` matches `\bbreaking\b` across the whole output and flags a breaking-change claim whenever the word appears — the same phrase-versus-assertion mistake, now visible because no fact is breaking anymore. The flags are advisory and do not fail a run, and separating a claim from prose that uses the word needs more than a regex, so it is filed separately. ([#70](https://github.com/goldbarth/chartula/pull/70))

## Refactoring

### Features

- **`preview` and `generate` commands.** Run `chartula preview` or `chartula generate` with `--tag` and `--repo <owner/name>`. `generate` writes `changelog.json`, `CHANGELOG.md` and the GitHub release notes; `preview` runs the identical flow, including generation, so you see the real result, but writes and publishes nothing. Both print a usage screen, a readable per-audience summary, and clear messages for unknown commands, a missing `--tag` or an invalid `--repo` instead of crashing. `--repo` must be given explicitly for now, and review mode uses the auto-approve reviewer until the interactive console reviewer is built.

- **Configuration from `chartula.yaml`.** Chartula now reads `chartula.yaml` (or `.yml`) and works with no configuration at all — every option falls back to its default. Environment variables override values from the file. A minimal `chartula.example.yaml` ships in the repository root: copy it to `chartula.yaml` and uncomment what you need. The full option set and defaults are in `docs/configuration.md`. Invalid values are reported as a clear `Configuration error: ...` message rather than an unhandled exception.

- **`categories` configuration section.** Control how categories are presented with `order`, `names` and `breakingProminent` (default `true`). Sections stay independently editable — untouched sections keep their defaults — and an unknown category name is rejected with a clear message naming the valid categories. Documented in `docs/configuration.md`.

- **Configurable fact-base depth.** Choose how much source material feeds the fact base via `Chartula:FactBase:Depth`: title only, title plus PR description (the default), or title, description and linked issues. The setting accepts the canonical names plus the aliases `title`, `description` and `full`, and an unknown value fails at startup with a clear error.

- **Label rules from configuration.** Steer curation with GitHub labels under `Chartula:Labels`, without touching code: a label can exclude a pull request, force it into a given category, or you can switch on an "only include labeled pull requests" mode. Matching is case-insensitive, all of it is optional, and an unknown category name fails at startup with a clear error listing the valid categories.

- **Internal and chore changes filtered out by default.** Filtering is based on category and labels rather than guesswork. The excluded set defaults to internal changes and can be replaced through `Chartula:Filter:ExcludeCategories`. A breaking change is never dropped for being in an excluded category, though an explicit label exclusion still takes precedence.

- **Deterministic categorization before any generation.** Categories are decided in code from Conventional Commit titles — feature, fix, performance, documentation, refactor and internal — with `Other` as the default for unrecognised or prefix-less titles. Breaking changes are tracked separately via a `!` marker, a `breaking` type or a `BREAKING CHANGE` footer, so a breaking feature stays a feature while still being flagged.

- **Release history and pull requests read from your repository.** Given a tag, Chartula determines the commits since the previous tag, or all history when there is no previous tag (first release), with clear errors for unknown or blank tags. It then retrieves the merged pull requests associated with those commits — title, description, labels, number and link — keeping merged ones only and de-duplicating across commits. `GITHUB_TOKEN` is optional; public repositories work unauthenticated, subject to rate limits. API, network and malformed-response failures produce a clear error rather than a crash.

- **Graceful handling of imperfect pull request discipline.** With no associated pull requests, Chartula falls back to commit data. A blank or uninformative title (such as `WIP`, `update` or a merge subject) falls back to the first informative line of the pull request body, then to a generic `PR #n`. An empty release yields an empty set rather than an error, so a run never hard-fails purely because pull request hygiene was imperfect.

- **A grounded fact base per release.** Each included change becomes one structured record holding its title, pull request number and link, category, user-visible and breaking flags, linked issues and an optional description. Linked issues are parsed from GitHub closing keywords (`closes/fixes/resolves #n`) in the title and body, categories and flags come from the deterministic curation steps, and filtered-out changes are dropped. Nothing in the record is produced by an LLM.

- **`changelog.json` as a durable record.** The fact base is written to `changelog.json` in a stable, documented, parseable format, with `schemaVersion` as the contract consumers can check. Fields are always present, including `null` values. The schema, field types and stability rules are documented in `docs/changelog-json.md`.

- **All audience texts stored in `changelog.json`.** The customer and product-manager texts now live in a `renderings` object keyed by audience (`technical`, `customer`, `product`) inside the one file, so no separate marketing files are written into your repository. When no renderings are supplied, the object is present but empty. `schemaVersion` stays `1`, since adding an optional field is non-breaking and older consumers simply ignore it.

- **`CHANGELOG.md` written with history preserved.** Each release is added as a new section at the top of the file, and existing sections are kept verbatim. A brand-new file gets a `# Changelog` title. Re-running the same tag replaces that section in place, keeping its position, so re-running an older release never moves it above a newer one and running the same release twice produces a byte-identical file.

- **Generated text published to the GitHub release notes.** Chartula looks up the release by tag and updates it in place if it exists, or creates it otherwise, and returns the release URL. Because GitHub keys a release by its tag, re-running for the same tag updates that one release rather than creating a duplicate. API and network failures surface as clear errors.

- **Three audiences from one fact base.** Technical, customer and product-manager versions are rendered from the same set of established facts, so they cannot contradict each other. Audience selection happens in code, not in the model: the customer text omits non-user-visible changes and their links, the technical text keeps jargon, links and the full change set, and the product-manager text sees the full set grouped by theme. A failure on one audience does not affect the others.

- **Prompting that rephrases facts and never invents them.** The model is instructed to introduce no fact, number or name that is not in the supplied list, to treat each fact's category and `(breaking)` marker as established rather than something to change or infer, and to stay brief on thin facts rather than padding or speculating. Categories and flags are handed to the model as text, not decided by it, and the user prompt carries only the facts.

- **Generation through a provider-agnostic interface.** Changelog generation makes exactly one model call per release, and no call at all for an empty fact base. Provider failures are returned as a failed result carrying the release tag and the provider's message rather than crashing the run. The LLM provider itself sits behind a single interface with Anthropic as the first provider; model and provider are selectable via configuration and the API key is read from an environment variable, never hardcoded. Swapping providers is a configuration and wiring change only.

- **Consistent formatting and tone per rendering.** Model output is normalised with conservative, structure-preserving rules — consistent line endings, a single `- ` bullet marker, trimmed trailing whitespace and collapsed runs of blank lines — while headings and prose are left intact. The prompt additionally asks for one consistent voice and format, so an individual author's tone or phrasing is not carried over.

- **Free rule-based hallucination check, always on.** Before any LLM check, generated output is compared against the fact base and passages are flagged when a number does not appear in the facts, a quoted or backticked name is not present (the usual shape of an invented API or option name), or a breaking change is claimed when no fact is marked breaking. The check makes no model call and costs zero tokens. Flags are advisory: they surface passages for review rather than failing a run.

- **Thorough second-pass check for meaning-level errors.** A second LLM pass compares the text semantically against the fact base and flags unsupported claims — catching distortions the rule-based check cannot see, such as "bug fixed" becoming "security hole closed". It is on by default and can be switched off with the `Chartula:Faithfulness:Thorough` key; when disabled, or when there is nothing to check, no LLM call is made.

- **Opt-in review mode.** Review is off by default and text passes straight through. When switched on via `Chartula:Review`, each rendering is presented to a reviewer with the flagged passages from both faithfulness checks highlighted, and the reviewer can approve the text as-is or return an edited version — whichever text results is what gets written.

- **Run metrics after every run.** Every `preview` and `generate` run now ends with a summary of what it did and what it cost: how often each check ran and how often it found something, and tokens in and out per operation. One indented line pairs the claims that **only** the thorough check caught with the tokens it spent catching them — claims both checks find are excluded, because there the thorough check adds nothing over the free one — so across a few releases you can tell whether those tokens are buying anything. Measurement is a side channel: a run without it produces byte-identical output. `docs/run-metrics.md` explains how to read the summary and make the keep-or-drop call.

### Fixes

- **Generated text is no longer truncated.** Calls went out without an output-token ceiling, so the provider substituted its own default of 1024 and all three audience texts were cut off mid-word — reported as a successful run, while the thorough check spent 56,712 tokens flagging the severed sentence as an unsupported claim. The ceiling is now always sent, configurable via `llm.maxOutputTokens` and defaulting to 16000. On a real release run, rephrasing output went from 3,072 tokens to 11,271 and texts end in complete sentences.

- **Prose about breaking changes is no longer labelled breaking.** `BREAKING CHANGE` was matched as a case-insensitive substring anywhere in the body, so text merely *discussing* breaking changes *declared* one — six of the thirty-three changes in v0.1.0 were mislabelled, none of them breaking. The marker is now matched as the Conventional Commits footer: uppercase, at the start of a line and colon-terminated. The same real run went from six reported breaking changes to zero.

- **Known limitation, not fixed here.** The rule-based check still matches the word "breaking" anywhere in the output and flags a breaking-change claim whenever it appears — the same phrase-versus-assertion confusion, now more visible since no fact is marked breaking. These flags are advisory and do not fail a run, and telling a claim apart from prose that merely uses the word needs more than a regular expression, so it has been filed separately rather than rushed in.

**Feature** — Given a tag, Chartula determines the commit range since the previous tag, falling back to all history when there is no previous tag (a first release). Unknown or blank tags produce clear errors.

**Feature** — For that commit range, Chartula retrieves the associated merged pull requests from the GitHub API, keeping merged PRs only and de-duplicating them.
