### What's New

- **Release binaries:** Releases now include ready-to-run binaries for six platforms instead of a NuGet package. Anyone downloading one can run it directly, without installing the .NET SDK first.
- **Technical entry formatting:** Technical changelog entries now show command names, options, configuration keys, files, types and methods as code-formatted text, spelled exactly as given. You can trust that every such name matches what appears in the project rather than a shortened or reworded version.
- **Changelog file provenance:** changelog.json can now include a record of how it was produced: the tool version, the model provider and model used, and a hash of the prompt. It's included only when that information is available, so the file's existing format is unaffected when it isn't.
- **Default model and audiences:** A run with no options now defaults to the Claude Sonnet 5 model and renders both the technical and customer changelogs; the product changelog renders only when you ask for it by name. You can still choose any audience combination or model yourself.
- **Release start:** A release for a project's first tag no longer renders its entire commit history automatically. You decide where the release starts: pass --since \<ref> to begin after a previous point, or --whole-history to render everything on purpose.
- **Release notes drafts:** GitHub release notes written by a run are now created as a draft rather than published immediately, so you can review them before the release goes live. Updating an already-published release still updates it in place without turning it back into a draft.
- **Automatic tag and repository:** Running the tool inside a git checkout no longer requires passing --tag or --repo. The nearest tag and the repository are picked up automatically and shown before the run starts, so you can still override either flag directly when you need to.
- **Model setting validation:** A configuration combining a thinking mode with a model that rejects it is now caught before the run starts, instead of failing partway through after fetching data and calling the model. The error message names the setting to change.
- **Changelog entry structure:** Every change in a release now gets its own entry in the generated changelog rather than being grouped into a collapsed summary line. Entries for technical, customer, and product readers follow a consistent, predictable structure in each run.
- **Changelog templates:** Technical and product changelogs now follow fixed templates: technical entries are grouped into Changed, Added and Fixed with breaking changes listed first, and CHANGELOG.md opens each release with its version and date. Internal work, documentation, and refactors are left out of both unless they are breaking or specifically labelled.
- **Pull request labels in changelog.json:** changelog.json now carries the labels from each pull request alongside its other details, exactly as they were applied. This makes it possible for future renderings to group or tag changes by subject matter rather than only by change type.
- **Selecting audiences:** A run can now render only the audiences you name with --audience, instead of always producing all three. You no longer pay for calls to audiences you don't read; leave the option off and every audience still renders as before.
- **Customer changelog ordering:** The customer changelog now puts entries that ask you to act above ones that don't, with a breaking change always listed first, and groups no longer end with a trailing summary line. Vague claims like "faster" or "more reliable" are left out unless the entry gives you something to check them against.
- **GitHub token warning:** A run started without a GitHub token now prints a warning before doing any work, noting the lower request limit that applies without one and how to set it. The run still continues unauthenticated; nothing is required unless you want the higher limit.
- **Published release page:** A run now writes release-\<tag>.md, a ready-to-publish page for the customer changelog, with a title, description, and publish date drawn from the release. A release with nothing for that audience produces no page at all.
- **Generate without publishing:** A --no-publish option now writes changelog.json and CHANGELOG.md without creating or updating a GitHub release, and the run lists what it wrote and what it skipped. Without the flag, generate still writes and publishes as before.
- **OpenAI-compatible provider:** The llm.provider setting now also accepts openai-compatible, letting a run send its model calls to any endpoint speaking the OpenAI chat-completions format, including one hosted on your own machine so release data never has to leave it. Both the model and the endpoint address must be set explicitly for this provider; there is no default to fall back on.
- **Model thinking mode:** A new llm.thinking setting lets you choose whether the model reasons before answering, instead of that being decided silently by whichever model you picked. Left at its default it behaves as before, and can be set to disabled or adaptive depending on the model, so the cost of a run is a decision rather than a surprise.
- **Run cost summary:** Every preview and generate run now ends with a summary of how many checks ran, how many claims they found, and how many tokens each spent, including what the deeper check caught that the free one missed. You can use this to judge whether the deeper check is worth its cost on your own releases.
- **Category configuration:** A new categories section in chartula.yaml lets you set the order categories appear in, rename their display labels, and control whether breaking changes are shown prominently. An unknown category name in the configuration is rejected with a clear error.
- **Configuration file:** The tool now reads settings from a chartula.yaml file when one is present, letting you refine behaviour such as how much detail each change carries; with no file, it runs with sensible defaults. An invalid value in the file is reported as a clear configuration error instead of a crash.
- **Generate and preview commands:** The tool now has two commands: generate, which produces and publishes a release's changelog, and preview, which runs the same process but writes and publishes nothing, so you can see the result first. Both take --tag and --repo and report clear errors rather than crashing.
- **GitHub release notes:** A generate run now writes its generated text directly to the release's GitHub notes, creating the release if it doesn't exist yet. Running it again for the same tag updates those notes in place rather than creating a second release.
- **CHANGELOG.md history:** Each release is now written as a new section at the top of CHANGELOG.md, with earlier sections kept untouched below it. Running the same release again replaces its section in place instead of duplicating it.
- **Review mode:** An optional review mode lets you look over each generated text and its flagged passages before anything is published, approving it as written or editing it yourself. It stays off by default, so nothing changes unless you turn it on.
- **Thorough faithfulness check:** A second, deeper check now looks for subtle wording that oversells what a change actually does, such as a bug fix described as closing a security hole, catching things a simple check can't see. It runs by default and can be turned off with a single setting.
- **Rule-based faithfulness check:** Every generated text is now checked, at no extra cost, for numbers, quoted names, or breaking-change claims that don't appear anywhere in the source facts. Flagged passages are surfaced for review rather than blocking the run outright.
- **Audience renderings:** A release now produces three versions - technical, customer, and product - all drawn from the same underlying facts, so they can never disagree on what changed. The customer version leaves out changes that aren't user-visible, while the technical version keeps full detail and links.
- **Rephrasing only:** Generated text is now built strictly by rephrasing the established facts of a release, never adding anything that isn't already known. A release with little to say produces a short entry rather than a padded one.
- **Changelog generation:** The tool can now generate a changelog by calling a language model through a single, swappable interface, with a release that has no changes making no call at all. A provider failure is reported clearly rather than crashing the run.
- **Source detail level:** A new setting lets you choose how much detail from each pull request feeds its changelog entry: title only, title plus description (the default), or title, description, and linked issues. An unrecognized value is rejected with a clear error at startup.
- **Release fact base:** Each change in a release is now assembled into a complete, structured record - category, breaking status, reader visibility, and linked issues - before any text is generated. This record comes entirely from deterministic rules, never from the model.
- **Change records:** Each change now has its own structured record of established facts - title, link, category, visibility, and linked issues - that generated text may only rephrase from, never add to.
- **Internal changes filtered:** Internal and chore-type changes are now left out of the changelog by default, while breaking changes are never dropped regardless of their category. The excluded categories can be changed in configuration.
- **Label-based curation:** GitHub labels can now steer what appears in the changelog: a label can exclude a change, force it into a particular category, or require a label for inclusion at all. All of this is optional and set in configuration; with no labels, nothing changes.
- **Change categorization:** Each change is now assigned a category - feature, fix, performance, documentation, refactor, internal, or other - based on its commit prefix, decided before any text is generated. Breaking changes are flagged separately, so a breaking feature still shows as a feature while being marked breaking.
- **Fallback for missing pull requests:** When a release has no associated pull requests, or a pull request has an uninformative title like "WIP", the changelog now falls back to the commit message or the pull request's description rather than leaving that change out. A release with nothing to report simply produces an empty result rather than failing.
- **Changes grouped by pull request:** Changes are now summarized per merged pull request rather than per raw commit, using each pull request's title, description, labels, and link. A failure reaching the GitHub API is reported clearly rather than crashing the run.
- **Release commit range:** The tool now works out exactly which commits belong to a release by reading git directly, covering both an ordinary release since the previous tag and a first release with no previous tag to compare against.
- **Model provider setup:** The tool now generates changelog text through a single interface that can work with different language model providers, starting with Anthropic's. The API key is read from your environment or configuration rather than being built into the tool.

### What's Changed

- **Testing dependencies:** Testing tools used to build the project were updated to their latest versions.
- **Dependency updates:** The libraries the tool depends on for AI model calls were updated to their latest versions.
- **Project setup:** The project's initial structure, license, and documentation were established.

### Bug Fixes

- **Reverted changes:** A change that was reverted within the same release could previously still show up in the changelog as if it shipped. Reverted pull requests and the commits that reverted them are now matched and left out together, so the changelog only shows what actually shipped.
- **Truncated model responses:** A changelog could previously be generated from a prompt that was cut off partway, with the missing instructions and facts never flagged as a problem. A run now fails loudly whenever a model's response doesn't fit what it reasonably should, for both rephrasing and the faithfulness check, naming the problem instead of producing an incomplete result.
- **Pull request template text:** A pull request description was previously picked up as-is even when it was only hidden comments or an unfilled template, letting placeholder and example text leak into the changelog. Hidden comments are now stripped and an untouched template is treated as if no description was given, so only what the author actually wrote reaches the generated text.
- **Insecure endpoint addresses:** An endpoint address pointing to another machine over plain http could previously send credentials in the clear. Such addresses are now refused at startup unless they use https or point at your own machine, with an error naming the setting and value to fix.
- **Endpoint and credential settings:** chartula.yaml could previously set the model endpoint, its credential variable name, the GitHub endpoint, and its token variable name, even though that file is part of the repository and these settings control where release data and credentials go. Those four settings must now be set as environment variables instead; a leftover value in chartula.yaml is refused at startup, naming the environment variable to use.
- **Git executable resolution:** A git executable committed inside the repository being read could previously run instead of the real git, with full access to your environment and keys. The tool now always resolves git from your system PATH, and a machine without git is refused before any work starts.
- **Draft release updates:** Updating a draft release's notes could previously detach it from its tag, causing the next run to create a second draft instead of finding the first. The update now keeps the tag attached, so re-running updates the same draft.
- **Exit status on partial failure:** A run where one requested audience failed to render previously still reported success and could overwrite an existing changelog with an incomplete one. The command now exits with an error whenever any audience fails, writes only what did render, and leaves prior files untouched when nothing rendered at all.
- **Missing API key:** Running against the Anthropic provider without an API key previously fetched pull requests from GitHub before failing on the first model call. The missing key is now caught immediately, before any request goes out, naming the environment variable to set.
- **Angle brackets in generated text:** Text written by the model could previously render incorrectly wherever it included angle brackets outside of code formatting. Such brackets are now escaped automatically in every changelog and release notes file, so they display as written.
- **Faithfulness check accuracy:** The thorough faithfulness check could previously flag a correct pull request link as unsupported because it wasn't given the reference to compare against. It now receives the same pull request number and link the generated text carries, so a correct reference is no longer flagged by mistake.
- **Faithfulness check on truncated prompts:** A faithfulness check whose prompt was cut off by the endpoint could previously come back with a clean verdict, since the model never saw what it was supposed to verify. Such a check now fails the run instead of reporting a false clean result.
- **Customer entry clarity:** A customer changelog entry could previously describe only what changed and never what it means for you, because the instructions said what not to write without saying what to write instead. Entries now state what you can rely on going forward, taken from the facts of the change.
- **Visibility of changes:** Every change of a given type, such as a new feature, was previously shown to customers regardless of whether it was something a user could actually see or use. Whether a change reaches the customer changelog is now decided by a label on the pull request when one is set, falling back to its category only when no label applies.
- **Customer entry wording:** An entry about a configurable setting could previously name only where to set it without saying what choosing it gets you. Such entries now state what you can rely on first, with the place to change the setting following it.
- **Customer changelog cut short:** Long customer changelogs could previously come back empty, because the model ran out of room to write after reasoning through its answer. The limit on how much it can write has been doubled, from 16,000 to 32,000, so both the thinking and the final text have space to complete.
- **Missing customer page:** A customer changelog could previously come back as an empty page when the model's entire answer was mistaken for just the page's description, leaving nothing in the body. The full answer is now kept as the body whenever stripping out a description would leave nothing behind.
- **Customer entry outcomes:** A customer changelog entry could previously leave out what a change means for you, since that part was optional. It now has to be included, so every entry says what you can rely on rather than only what changed.
- **Customer changelog consistency:** The customer changelog's shape - grouping, wording, and what counts as jargon - previously varied between runs and models, since nothing specified it. It now follows a fixed structure: changes are grouped consistently, entries open on what you observe rather than the work behind it, and a setting is only mentioned together with where to change it.
- **Unreadable faithfulness check:** A thorough faithfulness check that could not read the model's answer previously reported the same as a check that found nothing, so a run looked clean when nothing had actually been verified. The run summary and review flags now say when a check could not be read, distinct from one that checked cleanly.
- **Breaking-change flag accuracy:** The free faithfulness check previously flagged any mention of the word "breaking" as an unsupported claim, even in a sentence merely describing the breaking-change feature itself, creating flags that taught reviewers to ignore them. That check no longer looks for breaking-change claims; the deeper check, which understands meaning rather than matching a word, covers this instead.
- **LLM call reporting:** A model call that reported no token usage could previously look identical to one that used very few tokens in the run's reporting.
- **Truncated output and false breaking flags:** Generated text could previously be cut off mid-word because no limit was sent to the model, and unrelated prose that simply discussed breaking changes could be mislabelled as one. Output now completes in full since a configurable limit is always sent, and only an actual breaking-change marker in a commit is treated as one instead of the word appearing anywhere in the text.
