### What's New

- **Self-contained release binaries:** Chartula is now distributed as a self-contained binary for each supported platform, downloaded from a release rather than installed through a package manager. You can run it without installing the .NET runtime first.
- **Code-formatted technical identifiers:** The technical changelog now writes command, option, configuration, file, type and method names as code-formatted text, taken exactly as the source material spells them.
- **Changelog provenance record:** The generated changelog.json file can now include a provenance record stating the tool version, the AI provider and model, and a hash of the prompt used to produce it. It is included whenever that information is available, so you can trace how a given file was produced.
- **Default rendering audiences:** A run with no audience specified now renders the technical and customer changelogs by default, leaving out the product one unless you ask for it by name with --audience.
- **Release start on first tag:** Running against a first tag now stops with an error instead of silently rendering the project's entire history as one release. Use --since to mark where the release should start, or --whole-history if you really do want everything included.
- **Draft release notes:** Generated release notes are now published as a draft rather than going live immediately, so you can review them before publishing. Re-running the tool updates that same draft instead of creating another one.
- **Defaulted tag and repo:** Running chartula from inside a git checkout no longer requires passing --tag or --repo: both are now read from the checkout itself. You can still override either flag, and the tool tells you on screen which values it defaulted to before it runs.
- **Thinking mode validation:** Setting a thinking mode the configured Anthropic model does not support now stops the run at startup with a configuration error, instead of failing partway through after GitHub and model calls have already been made.
- **Consistent rendering structure:** Every rendered changelog entry's structure - its heading, grouping, breaking-change marker and reference - is now assembled by the tool itself rather than left to the model, so the same release renders the same way regardless of which model produced the wording. The model no longer collapses minor changes into a single combined line; each change gets its own entry.
- **Audience templates:** The technical, customer and product changelogs now each follow a defined template rather than loose tone guidance, and entries about internal work, documentation or refactors are left out of the technical and product changelogs unless labelled or breaking. CHANGELOG.md section headings now show the version and date together.
- **Labels in changelog.json:** The generated changelog.json file now carries the labels of each change, exactly as applied to its pull request.
- **Selectable audiences:** The --audience option now lets you render only the technical, customer or product changelog, or any combination of them, instead of always generating all three.
- **Customer entry ordering and claims:** The customer changelog now puts entries that ask something of you above the ones that don't, groups minor changes under one closing note instead of listing each separately, and leaves out vague claims like "much higher" when there's nothing to measure them against.
- **Missing GitHub token warning:** A run that starts without a GitHub token now prints a warning before doing any work, naming the practical rate limit and how to set a token, instead of only failing partway through once the limit is reached.
- **Standalone release notes page:** Each release now also produces release-\<tag>.md: a publishable page of the customer changelog with a title, description and publish date. A release with nothing for that audience produces no page at all.
- **Generate without publishing:** The generate command now accepts --no-publish, which writes changelog.json and CHANGELOG.md without publishing the GitHub release notes, and lists what it skipped alongside what it wrote.
- **OpenAI-compatible provider:** You can now point Chartula at any OpenAI-compatible endpoint, including one running on your own machine, instead of only Anthropic. Set llm.provider to openai-compatible and give it a model and base URL, so release data can stay on your own hardware if you choose.
- **Configurable model thinking:** You can now set llm.thinking to control whether the model reasons before answering, instead of relying on whichever default a given model happens to use. The setting applies only to Anthropic models, and some combinations of model and thinking mode are rejected since the model does not support them.
- **Run metrics summary:** Every preview and generate run now ends with a metrics summary showing how many checks ran, how many claims each one caught, and how many tokens each step spent - including how many claims the thorough check caught that the free check missed, so you can judge whether it's worth the tokens it costs.
- **Configurable categories:** You can now configure the order, display names and breaking-change prominence of changelog categories in chartula.yaml, instead of relying on fixed built-in settings.
- **Project configuration file:** Chartula can now read settings from a chartula.yaml file in your project, refining behavior such as fact-base depth and thoroughness of the faithfulness check, while continuing to work with sensible defaults if no file is present.
- **Preview and generate commands:** Chartula now has preview and generate commands: generate renders and writes the changelog, release notes and GitHub release; preview runs the same pipeline but writes and publishes nothing, so you can see the result first.
- **GitHub release notes:** Generated changelog text is now written to the GitHub release notes for the tag, creating the release if none exists and updating its notes in place on later runs rather than creating a duplicate.
- **CHANGELOG.md history:** Each release now gets prepended to CHANGELOG.md as a new section, keeping all earlier sections intact. Running the same release again replaces its section in place instead of duplicating it.
- **Review mode:** You can now turn on a review step that shows you each generated text together with any flagged passages before it's written, letting you approve it as-is or edit it. It's off by default, so nothing changes unless you turn it on.
- **Thorough faithfulness check:** A second, more thorough check can now catch subtle hallucinations in generated text that a simple check would miss, such as a fix being rendered as something it wasn't. It's on by default and can be turned off with a single setting.
- **Rule-based faithfulness check:** Generated changelog text is now checked against the source facts for invented numbers, names and breaking-change claims before you ever see it, at no extra cost since the check runs without calling the model.
- **Multi-audience rendering:** Chartula now produces technical, customer, and product-manager versions of each release from the same underlying facts, so the three can never disagree with each other on what changed.
- **Fact-grounded prompting:** Generated changelog text is now built from a prompt designed to only rephrase the established facts of a release, never invent details, and stay brief rather than pad out a thin set of changes.
- **Changelog generation:** Chartula can now actually generate changelog text through the configured AI provider for a release, and reports a clear failure rather than crashing if the provider call fails.
- **Configurable fact-base depth:** You can now choose how much detail feeds each change's description - title only, title and pull request description, or title, description and linked issues - instead of a single fixed level of detail.
- **Release fact base:** Chartula now assembles a complete fact base for a release from its curated changes, including linked issues parsed from closing keywords in each pull request.
- **Change fact model:** Every change in a release is now captured as a structured fact - title, PR number, link, category, user-visible and breaking flags, linked issues - recorded from deterministic data rather than generated by the model.
- **Default category filtering:** Internal and chore changes are now left out of the changelog by default, while a breaking change is never dropped even if its category would otherwise be excluded. You can override which categories are excluded in configuration.
- **Label-based curation rules:** You can now steer which pull requests appear in the changelog and under which category using GitHub labels, configured in chartula.yaml - exclude a PR, force its category, or require a label before it's included at all. None of this is required; the tool works the same with no labels in use.
- **Deterministic change categorization:** Each change's category - feature, fix, performance, docs, refactor, internal, or other - is now determined from its Conventional Commit prefix before any AI involvement, with breaking changes tracked and flagged separately.
- **Fallback for missing PR data:** When a release has no associated pull requests, or a pull request's title is blank or uninformative, the changelog now falls back to the commit message or the pull request's description instead of leaving that change out.
- **Pull request based summaries:** Changes are now summarized per merged pull request rather than per raw commit, using each pull request's title, description, and labels.
- **Release commit range:** Chartula can now determine exactly which commits belong to a release by reading the commit range since the previous tag, including the case where there is no previous tag yet.
- **AI provider integration:** Chartula can now generate changelog text through a pluggable AI provider, starting with Anthropic, with the API key read from your environment rather than hardcoded.

### What's Changed

- **Test tooling updates:** Several testing-related dependencies used to build and test Chartula were updated to their latest versions.
- **Dependency updates:** Several underlying library dependencies used by Chartula were updated to their latest versions.
- **Initial project setup:** The initial project structure, license and documentation for Chartula were put in place.

### Bug Fixes

- **Revert pairing in changelog:** A pull request that reverted earlier changes no longer appears as if those changes still shipped: the reverted pull requests are now removed from the changelog, and the revert itself is left out when everything it reverted was part of the same release. You can rely on a revert that only partly matches changes in the release still being shown, so a change you may have already seen stays visible.
- **Truncated prompt detection:** A pull request description or title truncated by a model endpoint could previously still produce changelog entries or a clean faithfulness check, as if nothing were missing. Both now fail with a clear error naming the context-window problem, so you no longer have to wonder whether a suspiciously clean result is accurate.
- **Clean pull request descriptions:** A pull request's description could previously carry over hidden template comments or an unfilled template's headings and checklist boxes as if they were real change notes. Both are now left out, so you can rely on the description only ever showing what the author actually wrote.
- **Required HTTPS for endpoints:** A configured GitHub or AI provider endpoint using plain http to a remote host previously went through unchanged, sending credentials in the clear. Chartula now refuses to start in that case, requiring https for any endpoint other than one on your own machine.
- **Environment-only endpoint settings:** Endpoint URLs and credential variable names could previously be set in chartula.yaml, a file that lives in the repository, letting it quietly redirect where release data and credentials get sent. These settings can now only be set via environment variables, and Chartula refuses to start if chartula.yaml still sets one, naming the environment variable to use instead. Every run now prints the endpoints and credential variable names it's using, without ever printing their values.
- **Trusted git resolution:** Chartula could previously run a git executable placed inside the checkout being read, picking up a committed file instead of the real git on your system. It now always resolves git from your PATH, so a run can no longer be hijacked by a file sitting in the project it's reading.
- **Draft release tag retention:** Updating an existing draft release's notes could detach the draft from its tag, causing the next run to create a second draft instead of updating the first. The tag is now kept on every update, so re-running stays on the one draft.
- **Exit status on partial failure:** When one of several requested changelog audiences failed to render, the run previously still exited successfully and could overwrite an existing changelog.json with an incomplete result. The run now exits with an error whenever any requested audience fails, and leaves existing files untouched if nothing rendered at all.
- **Missing API key check:** Running with the Anthropic provider configured but no API key set previously let the run proceed through GitHub and fail only once it reached the model, with a raw error for every audience. It now stops immediately with a clear configuration error naming the missing variable, before any GitHub request is made.
- **Angle bracket rendering fix:** Angle brackets written by the model outside of code spans, such as in a reference like release-\<tag>.md, previously rendered incorrectly in the generated changelog and release notes. They are now escaped automatically, so you can rely on such text displaying as written.
- **Faithfulness check PR references:** The thorough faithfulness check previously could not confirm a pull request reference in generated text, since it wasn't given the reference to check against. It now receives each change's pull request number and link, so it can rely on checking references properly rather than flagging them as unsupported.
- **Truncated faithfulness check detection:** A faithfulness check could previously return a clean result even when the request was truncated before reaching the model, reporting no issues found instead of an actual failure. The check now fails the run when the amount of input the endpoint reports could not possibly include everything that was sent.
- **Customer entry outcome wording:** Generated customer changelog entries could previously state what changed without ever saying what it means for you, restating the change rather than its outcome. The customer wording guidance now makes clearer where that outcome should come from, so entries are more likely to state what you can now rely on rather than just what changed.
- **Label-based change visibility:** Whether a change appeared in the customer changelog was previously decided mostly by its commit category, so routine internal changes could appear as user-facing simply because of how they were tagged. Visibility is now decided by labels when a pull request carries one, falling back to the category otherwise, so what reaches the customer changelog more reliably reflects what a reader can actually see.
- **Setting outcome before location:** Generated customer changelog entries that named a configuration setting could previously end on where to set it without ever saying what that setting gets you. The wording guidance now requires the outcome to be stated before the location, so an entry about a setting states what it does for you before where to configure it.
- **Increased output token budget:** Generated text could previously run out of room before finishing, because the model's internal reasoning and its visible answer shared too small a token budget, silently producing an empty customer changelog section. The available output space has been doubled so the model has room to finish writing after it's done reasoning.
- **Empty customer rendering fix:** A customer changelog rendering could previously come back completely empty if the model wrote only a release description with nothing else, since the description was mistakenly treated as replacing the body text. The description is now only extracted when there's a body left behind it, so a short rendering no longer disappears entirely.
- **Required customer outcome:** Generated customer changelog entries could previously omit what a reader gets out of a change entirely, since the wording rules allowed that part to be left out like any other. It's now a required part of every entry, so you can rely on each one stating what you can now count on, not just what changed.
- **Customer changelog format:** The customer changelog previously had no defined shape, so its grouping, wording and structure varied from one run to the next. It now follows a fixed format - defined groups and order, a four-part entry structure, required phrasing, and rules for where a reader needs to take action - so the result is more consistent across runs.
- **Unreadable faithfulness check reporting:** A thorough faithfulness check that failed to produce a readable result previously looked identical to a check that ran cleanly and found nothing wrong. Such a check is now reported and flagged as unreadable, so you can tell it apart from a genuinely clean result.
- **Breaking-change claim check removed:** The faithfulness check previously flagged any mention of the word "breaking" as an unsupported breaking-change claim, even in ordinary prose that only discussed the concept. That check has been removed; a genuine mismatched breaking-change claim is now left to the more thorough check instead.
- **Unreported call detection:** An AI provider call that returned no usable response previously looked the same as one that was never made, so you could not tell a failed call from one that cost nothing. (No further detail was given for this change.)
- **Truncated output and false breaking flags:** Generated changelog text could previously be cut off mid-sentence because the output limit was never set and defaulted too low, with the truncated text occasionally mistaken for an invented claim by the thorough check. A pull request's body text discussing breaking changes could also be wrongly marked as a breaking change itself. Both are fixed: the output limit is now set explicitly and configurable, and only an actual breaking-change marker in a pull request is treated as one.
